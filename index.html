01

Match the problem. Match the quality.

Use the same search space and success threshold. Document the classical baseline, quantum algorithm, and any assumptions about the oracle.

02

Account for the whole computation.

Separate oracle complexity from time-to-solution. Hardware evaluation should include compilation, execution, repetitions, mitigation, and classical processing.

03

Make the evidence reproducible.

Publish instance definitions, parameters, and raw results. Distinguish closed benchmarks with fixed implementations from open comparisons that fix success criteria and allow algorithm improvements.

UNDER THE HOODThe assumptions behind this model+

One marked item. An ideal oracle.

N = 2ⁿ possible states, one solution, and ideal noiseless gates. Classical random search without replacement uses ⌈pN⌉ queries for success probability ≥ p.

Grover uses θ = arcsin(1/√N), k = round(π/(4θ) − ½) iterations, and success s = sin²((2k+1)θ). Independent repetitions r = ⌈ln(1−p)/ln(1−s)⌉, with at least one run, give (k + 1) × r modeled oracle evaluations, including one classical verification query per run.

Timing is synthetic, not measured.

The runtime view assigns 1 μs per classical query and 80 μs per Grover iteration, plus 1 μs for classical verification after each run. Optional fixed overhead is 2 ms classical and 40 ms quantum. These values are deliberately illustrative, not device specifications. Grover iteration reference ↗

The model excludes oracle construction, state preparation, readout costs, gate decomposition, noise, error correction, and network or queue latency. Only the n-qubit search register is shown; oracle ancillas are excluded. Circuit depth, shots, fidelity, and confidence intervals require a real execution backend. This is fixed-budget workload timing, not an expected early-stopping runtime or a complete hardware time-to-solution measurement.
